# blockers

- **The evidence schema is trying to serve mutually incompatible “item types” without admitting it.** `EvidenceItem.content_text` as the canonical payload works for news/article and single-text codebook coding, but it is a lossy fit for the comparator lane implied by `Zheng/MT-Bench` (multi-turn dialogs, pairwise A/B outputs, rubric-plus-context). Either (a) drop the comparator lane in V4 wave 1, or (b) explicitly support structured evidence payloads in wave 1. Keeping comparator-in-scope while keeping “textual by default” is not credible.
- **“Universe/source/frame/import job” is too much schema for a first implementation wave, and it becomes a blocker because it forces migration complexity immediately.** Adding 6 new tables plus backfill plus dual-write is a multi-week integration tax that competes directly with producing a paper-quality audit. If wave 1 requires both “keep V3 running” and “new V4 audits,” the dual-write/backfill plan is the critical path, not the science.
- **Provider batching generalization is a hidden cross-cutting refactor that is not optional if you follow the proposed provider rollout literally.** The runtime plan correctly notes persisted batch artifacts are OpenAI-shaped (`*_file_id`). Supporting Anthropic message batches forces schema/UI refactors beyond “provider/runtime scope.” If the paper requires Anthropic at scale in wave 1, you must commit to “direct-only Anthropic” or you are blocked.
- **StagePlan generalization is not a “config-only” change in this repo as it exists today.** The current run system has fixed stage keys and counters. A truly generic `StagePlan` implies changes to: run orchestration, persistence, counters, UI/ops surfaces, and analysis expectations. If the study design depends on prompt replay + pairwise + label coding in wave 1, StagePlan becomes a blocking platform rewrite.
- **Paper scope currently assumes three hard things at once: faithful reconstruction, perturbation sweeps, and cross-provider controls across 3 targets.** This is not just “more experiments”; it is multiple distinct validity threats (reconstruction validity, perturbation validity, provider confounds) multiplied. Without a ruthless scope cut, the “self-contained paper” claim set will collapse under its own limitations section.

# overengineering risks

- **Schema overgeneralization via `*_json` blobs.** `spec_json`, `metadata_json`, `citation_json`, `license_json` everywhere will turn into an untyped data lake. That’s fine for long-term flexibility, but wave 1 needs a small number of strongly enforced invariants (stable sample IDs, provenance, and the exact fields required to render prompts). Over-flexibility early increases the chance you cannot reproduce your own runs.
- **`EvidenceItemView` is versioned but not governed.** `view_kind` and `pipeline_kind` as open strings plus `pipeline_version` as a free tag invites “accidental forks” where two views mean the same thing but are not comparable. That becomes an analysis nightmare, not a capability.
- **SamplingFrame/ImportJob are modeled as universal primitives, but you do not yet have evidence that you need both.** For wave 1, you likely have exactly two acquisition paths: existing windows and a small number of paper dataset imports. Modeling “all future ingestion” up front is classic schema sprawl.
- **OpenRouter is being treated as a clean provider-control, but it is actually an additional experimental factor (routing policy, upstream variability, parameter support variance).** Unless you freeze routing tightly (no fallbacks, explicit upstream constraints) it will confound “provider-family control” rather than support it.
- **Stage-plan complexity is being justified by task diversity, not by a wave-1 necessity.** A fully general stage runner (kinds, parsers, per-stage execution profiles, fidelity checks) is a platform. Platforms only pay off after you’ve shipped at least one complete end-to-end audit.
- **The study design mixes two papers worth of claims.** “Measurement language for evaluator geometry” plus “audit protocol” plus “multi-target empirical evidence” plus “provider expansion as a methodological control” is four contributions. A first-wave V4 paper needs one primary claim and one supporting demonstration, not four co-equal pillars.

# narrowings / sequence corrections

- **Drop the comparator lane from the first-wave V4 paper unless you are willing to explicitly support non-text evidence contracts.** Concrete narrowing: do not commit to `Zheng/MT-Bench` in wave 1; it drags in pairwise/multi-turn evidence modeling and StagePlan generalization.
- **Pick one lane as the “paper spine” and make the other lane explicitly future work.** Concrete narrowing: make wave 1 a paper-audit paper (Gilardi primary) and treat contested-concept news geometry as an optional appendix demo, not a co-equal lane.
- **Evidence schema: cut entities until you can state the wave-1 invariants in one sentence.** Concrete narrowing: for wave 1, require only stable `external_id` (or equivalent) for imported items, immutable raw payload, and an explicit rendered view used in each judgment; defer `SamplingFrame` and generalized `ImportJob` unless multiple importers truly need them.
- **Provider rollout: invert the “forces the right abstraction” logic. Optimize for shipping an audit first.** Concrete narrowing: support exactly one non-OpenAI provider in wave 1, direct-only, with batching explicitly out-of-scope; if OpenRouter is chosen, freeze routing (no fallbacks, conservative parameter requirements) and treat it as a router regime, not a clean provider control.
- **Stage plan: do not build a general stage runner in wave 1.** Concrete narrowing: extend the existing fixed stage pipeline only as far as needed to run a single paper audit (imported/frozen rubric or codebook; one scoring stage with a strict output contract).
- **Perturbation sweep: avoid a pseudo-factorial explosion.** Concrete narrowing: choose 2 perturbations max for wave 1 and keep them consistent; use abstention on/off plus exactly one of grouping change, evidence view change, or scale change.
- **Provider-control claims must be demoted unless you can isolate confounds.** Concrete narrowing: if you include a second provider, run it on a small pre-registered subset and report it as a robustness check, not a headline contribution.

# leanest defensible V4 verdict

V4 wave 1 should be: one paper-audit target (Gilardi) with a faithful reconstruction baseline plus two matched, one-lever perturbations, on OpenAI only; optionally add a single non-OpenAI direct-only robustness replicate on a fixed subset. Implementation-wise, V4 should introduce only the minimum evidence substrate needed to import a citable dataset with stable sample IDs and to record the exact rendered view used for each judgment, while keeping the existing fixed-stage runner (no general StagePlan) and deferring provider-native batching, OpenRouter routing policy, and comparator/pairwise task families.
